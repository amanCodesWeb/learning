# 0.6 Environment Configuration (.env)

## Overview

The **`.env` (Environment)** file stores environment-specific configuration such as database credentials, mail settings, cache driver, API keys, and application mode.

It allows the same application to use different configurations for **local**, **staging**, and **production** environments without changing the source code.

> **Note:** Laravel loads the `.env` file during application bootstrapping.

---

# Why Use `.env`?

- Keep sensitive information out of the source code.
- Easily switch between environments.
- Avoid hardcoding configuration values.
- Make deployment easier.

---

# Common Environment Variables

```env
APP_NAME=Laravel
APP_ENV=local
APP_DEBUG=true
APP_URL=http://localhost

DB_CONNECTION=mysql
DB_HOST=127.0.0.1
DB_PORT=3306
DB_DATABASE=laravel
DB_USERNAME=root
DB_PASSWORD=

CACHE_STORE=database
QUEUE_CONNECTION=database
SESSION_DRIVER=database

MAIL_MAILER=smtp
MAIL_HOST=smtp.mailtrap.io
MAIL_PORT=2525
MAIL_USERNAME=username
MAIL_PASSWORD=password
```

---

# How Laravel Uses `.env`

Read environment values using:

```php
env('APP_NAME');
```

In most cases, use the **`config()`** helper instead:

```php
config('app.name');
```

Example from `config/app.php`:

```php
'name' => env('APP_NAME', 'Laravel'),
```

Laravel reads the value from `.env` and stores it in the configuration.

---

# Important Variables

Variable > Purpose
--------------------
APP_NAME            > Application name
APP_ENV             > Current environment (local, production, testing)
APP_DEBUG           > Enable/Disable debug mode
APP_URL             > Base application URL
DB_*                > Database configuration
CACHE_STORE         > Cache driver
SESSION_DRIVER      > Session driver
QUEUE_CONNECTION    > Queue driver
MAIL_*              > Mail configuration

---

# Best Practices

- Never commit `.env` to Git.
- Commit only `.env.example`.
- Use `config()` instead of `env()` outside configuration files.
- Disable `APP_DEBUG` in production.
- Keep API keys and passwords inside `.env`.

---

# Common Mistakes

- Committing `.env` to version control.
- Setting `APP_DEBUG=true` in production.
- Using `env()` directly in controllers or services.
- Hardcoding database credentials in code.

---

# Interview Questions

### 1. What is the purpose of the `.env` file?

**Answer:**  
It stores environment-specific configuration such as database credentials, API keys, mail settings, and application mode.

---

### 2. Why should `.env` not be committed to Git?

**Answer:**  
Because it contains sensitive information like passwords, API keys, and database credentials.

---

### 3. What is the difference between `env()` and `config()`?

**Answer:**

- `env()` reads values directly from the `.env` file.
- `config()` reads values from Laravel's configuration files.
- In application code, prefer `config()` because configuration values can be cached.

---

### 4. What does `APP_DEBUG` do?

**Answer:**  
It controls whether detailed error messages are shown. It should be **false** in production.

---

### 5. Which file should be shared with other developers?

**Answer:**  
`.env.example`, not `.env`.

---

# Key Takeaways

- `.env` stores environment-specific configuration.
- Never commit `.env`; commit `.env.example`.
- Use `config()` in application code.
- Keep secrets such as API keys and passwords in `.env`.
- Set `APP_DEBUG=false` in production.
