# COMMIT, ROLLBACK & Savepoints

Transaction control statements for saving or undoing changes, with granular rollback points.

---

## COMMIT — Make Changes Permanent

```sql
-- Explicit commit
COMMIT;

-- Alias (MySQL)
COMMIT WORK;

-- With chain (start new transaction immediately)
COMMIT AND CHAIN;  -- MySQL, PostgreSQL

-- Release savepoints (optional)
COMMIT;  -- Implicitly releases all savepoints
```

### What COMMIT Does

1. Makes all changes visible to other transactions
2. Releases all row locks
3. Clears savepoints
4. Writes to WAL (Write-Ahead Log) for durability
5. Ends the transaction

```sql
-- Example: Order placement
START TRANSACTION;
INSERT INTO orders (user_id, total, status) VALUES (1, 99.99, 'pending');
SET @order_id = LAST_INSERT_ID();
INSERT INTO order_items (order_id, product_id, quantity, unit_price, total)
VALUES (@order_id, 1, 1, 99.99, 99.99);
UPDATE products SET stock = stock - 1 WHERE id = 1;
COMMIT;  -- All or nothing
```

## ROLLBACK — Undo Changes

```sql
-- Full rollback
ROLLBACK;

-- Alias
ROLLBACK WORK;

-- Rollback to savepoint
ROLLBACK TO SAVEPOINT savepoint_name;

-- Release savepoint (keep transaction open)
RELEASE SAVEPOINT savepoint_name;
```

### What ROLLBACK Does

1. Undoes all changes since `START TRANSACTION` (or savepoint)
2. Releases locks acquired in rolled-back portion
3. Does NOT release locks from before savepoint (if rolling back to savepoint)

```sql
-- Example: Failed payment
START TRANSACTION;
INSERT INTO orders (user_id, total, status) VALUES (1, 99.99, 'pending');
SET @order_id = LAST_INSERT_ID();
INSERT INTO order_items ...;

-- Payment fails
ROLLBACK;  -- Order and items deleted, stock restored
```

## Savepoints — Partial Rollback

```sql
-- Create savepoint
SAVEPOINT savepoint_name;

-- Rollback to savepoint (keeps transaction open)
ROLLBACK TO SAVEPOINT savepoint_name;

-- Release savepoint (can't rollback to it anymore)
RELEASE SAVEPOINT savepoint_name;
```

### Savepoint Rules

| Rule | Detail |
|------|--------|
| Names | Case-insensitive, unique per transaction |
| Nesting | Can create multiple, rollback to any |
| Release | `RELEASE` removes it and all later savepoints |
| Rollback to | Keeps earlier savepoints, removes later ones |
| COMMIT | Releases all savepoints |
| ROLLBACK | Releases all savepoints |

## Savepoint Example: Multi-Step Wizard

```sql
-- Step 1: Create order
START TRANSACTION;
INSERT INTO orders (user_id, status) VALUES (1, 'draft');
SET @order_id = LAST_INSERT_ID();
SAVEPOINT order_created;

-- Step 2: Add items (user can remove)
INSERT INTO order_items (order_id, product_id, qty) VALUES (@order_id, 1, 2);
SAVEPOINT items_added;

-- Step 3: Apply coupon (might fail)
INSERT INTO order_coupons (order_id, code) VALUES (@order_id, 'INVALID');
-- Error! Coupon invalid
ROLLBACK TO SAVEPOINT items_added;  -- Undo coupon, keep items

-- Step 4: Try valid coupon
INSERT INTO order_coupons (order_id, code) VALUES (@order_id, 'SAVE10');
SAVEPOINT coupon_applied;

-- Step 5: Confirm payment
-- ... payment processing ...
-- Success
COMMIT;
```

## Implicit Commits — Statements That End Transactions

**DDL statements cause implicit COMMIT in MySQL** (and some other DBs):

```sql
-- These cause implicit COMMIT in MySQL:
CREATE TABLE, DROP TABLE, ALTER TABLE
CREATE INDEX, DROP INDEX
TRUNCATE TABLE
RENAME TABLE
LOCK TABLES, UNLOCK TABLES
SET autocommit = 1 (if was 0)

-- Example:
START TRANSACTION;
UPDATE users SET name = 'Bob' WHERE id = 1;
CREATE TABLE temp (id INT);  -- IMPLICIT COMMIT! 'Bob' is now permanent
ROLLBACK;  -- Does nothing, transaction already committed
```

> **Rule**: Never mix DDL with DML in a transaction (MySQL). In PostgreSQL, DDL is transactional.

## Transaction Control in Application Code

### Pattern: Try/Catch with Rollback

```python
# Python pseudocode
def transfer(from_id, to_id, amount):
    conn = get_connection()
    try:
        conn.execute("START TRANSACTION")
        
        # Lock rows
        conn.execute("SELECT balance FROM accounts WHERE id IN (?, ?) FOR UPDATE", 
                     (from_id, to_id))
        
        # Check balance
        bal = conn.execute("SELECT balance FROM accounts WHERE id = ?", (from_id,)).fetchone()
        if bal < amount:
            raise InsufficientFundsError()
        
        # Transfer
        conn.execute("UPDATE accounts SET balance = balance - ? WHERE id = ?", (amount, from_id))
        conn.execute("UPDATE accounts SET balance = balance + ? WHERE id = ?", (amount, to_id))
        conn.execute("INSERT INTO transfers ...", (from_id, to_id, amount))
        
        conn.execute("COMMIT")
        return True
    except Exception as e:
        conn.execute("ROLLBACK")
        raise
    finally:
        conn.close()
```

### Pattern: Savepoint for Nested Operations

```python
def process_order(order_id):
    conn = get_connection()
    try:
        conn.execute("START TRANSACTION")
        
        conn.execute("SAVEPOINT order_start")
        
        # Reserve inventory
        reserve_inventory(conn, order_id)
        conn.execute("SAVEPOINT inventory_reserved")
        
        # Process payment
        process_payment(conn, order_id)
        conn.execute("SAVEPOINT payment_done")
        
        # Create shipment
        create_shipment(conn, order_id)
        
        conn.execute("COMMIT")
    except PaymentError:
        conn.execute("ROLLBACK TO SAVEPOINT inventory_reserved")
        # Inventory still reserved, can retry payment
    except ShipmentError:
        conn.execute("ROLLBACK TO SAVEPOINT payment_done")
        # Payment done, inventory reserved, refund payment
        refund_payment(conn, order_id)
        conn.execute("COMMIT")  # Commit refund
    except Exception:
        conn.execute("ROLLBACK")
        raise
```

## Autocommit Behavior

```sql
-- Check autocommit
SELECT @@autocommit;  -- MySQL (1=on, 0=off)
SHOW autocommit;      -- PostgreSQL

-- Disable for explicit transactions
SET autocommit = 0;

-- Re-enable
SET autocommit = 1;  -- Commits any open transaction!
```

### Autocommit + Implicit Commit Interaction

```sql
-- autocommit=1 (default)
UPDATE users SET name = 'Alice';  -- Auto-committed immediately

-- autocommit=0
SET autocommit = 0;
UPDATE users SET name = 'Bob';  -- Not committed yet
CREATE TABLE t (id INT);        -- Implicit COMMIT! 'Bob' committed
ROLLBACK;                       -- Nothing to rollback
```

## Transaction Isolation in Practice

```sql
-- Read committed: See only committed data
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
SELECT * FROM accounts WHERE id = 1;  -- Sees committed balance
-- Another transaction commits change
SELECT * FROM accounts WHERE id = 1;  -- Sees NEW balance (non-repeatable read)
COMMIT;

-- Repeatable read: Snapshot at transaction start
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT * FROM accounts WHERE id = 1;  -- Sees balance at START
-- Another transaction commits change
SELECT * FROM accounts WHERE id = 1;  -- STILL sees old balance
COMMIT;
```

## Performance: Keep Transactions Short

| Anti-Pattern | Problem | Fix |
|--------------|---------|-----|
| User input in transaction | Locks held for seconds/minutes | Get input first, then start transaction |
| Long-running SELECT in transaction | Blocks writes | Move reads outside or use lower isolation |
| Multiple round-trips | Network latency holds locks | Batch operations, use stored procedures |
| No timeout | Deadlocks hang forever | Set `innodb_lock_wait_timeout` |

```sql
-- Set lock wait timeout (MySQL)
SET innodb_lock_wait_timeout = 10;  -- 10 seconds

-- PostgreSQL: lock_timeout
SET lock_timeout = '10s';
```
