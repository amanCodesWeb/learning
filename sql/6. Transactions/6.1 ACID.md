# Transactions & ACID — Data Integrity

Transactions group multiple operations into a single **atomic** unit. Either all succeed or all fail.

---

## ACID Properties

| Property | Meaning | Guarantees |
|----------|---------|------------|
| **Atomicity** | All or nothing | Partial failure → full rollback |
| **Consistency** | Valid state → valid state | Constraints, triggers enforced |
| **Isolation** | Concurrent transactions don't interfere | Serializable appearance |
| **Durability** | Committed = permanent | Survives crashes/power loss |

---

## Transaction Syntax

```sql
-- Explicit transaction
START TRANSACTION;  -- or BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;  -- Make permanent

-- Rollback on error
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- Error! Insufficient funds
ROLLBACK;  -- Undo everything

-- Savepoints (partial rollback)
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
SAVEPOINT after_withdrawal;
UPDATE accounts SET balance = balance + 50 WHERE id = 2;  -- Wrong amount!
ROLLBACK TO SAVEPOINT after_withdrawal;  -- Undo only deposit
UPDATE accounts SET balance = balance + 100 WHERE id = 2;  -- Correct
COMMIT;
```

---

## Autocommit Mode

```sql
-- Default: autocommit = ON (each statement = transaction)
SET autocommit = 0;  -- Disable for explicit transactions
SET autocommit = 1;  -- Re-enable

-- Check current
SELECT @@autocommit;  -- MySQL
SHOW autocommit;      -- PostgreSQL
```

> **Best Practice**: Explicit transactions for multi-statement operations. Keep autocommit ON for simple reads.

## Isolation Levels — The Concurrency Trade-off

```
ISOLATION LEVELS (Strictest → Most Permissive)

SERIALIZABLE          ← Phantom reads prevented
    ↑
REPEATABLE READ       ← Non-repeatable reads prevented (MySQL default)
    ↑
READ COMMITTED        ← Dirty reads prevented (PostgreSQL, Oracle, SQL Server default)
    ↑
READ UNCOMMITTED      ← All anomalies possible (fastest, rarely used)
```

### Anomalies Prevented

| Level | Dirty Read | Non-Repeatable Read | Phantom Read |
|-------|------------|---------------------|--------------|
| READ UNCOMMITTED | ❌ Possible | ❌ Possible | ❌ Possible |
| READ COMMITTED | ✅ Prevented | ❌ Possible | ❌ Possible |
| REPEATABLE READ | ✅ Prevented | ✅ Prevented | ❌ Possible* |
| SERIALIZABLE | ✅ Prevented | ✅ Prevented | ✅ Prevented |

*MySQL REPEATABLE READ prevents phantoms via gap locks (InnoDB).

### Setting Isolation Level

```sql
-- Per transaction
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
...

-- Per session
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- Global (requires restart)
SET GLOBAL TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- Check current
SELECT @@transaction_isolation;  -- MySQL
SHOW transaction_isolation;      -- PostgreSQL
```

## Concurrency Anomalies Explained

### 1. Dirty Read
```
T1: BEGIN; UPDATE accounts SET balance = 500 WHERE id = 1;  -- Not committed
T2: SELECT balance FROM accounts WHERE id = 1;  -- Sees 500!
T1: ROLLBACK;  -- Balance back to 100
T2: Now has wrong data (500 never existed)
```
**Prevented by**: READ COMMITTED+

### 2. Non-Repeatable Read
```
T1: SELECT balance FROM accounts WHERE id = 1;  -- Returns 100
T2: UPDATE accounts SET balance = 200 WHERE id = 1; COMMIT;
T1: SELECT balance FROM accounts WHERE id = 1;  -- Returns 200!
```
**Prevented by**: REPEATABLE READ+

### 3. Phantom Read
```
T1: SELECT * FROM orders WHERE user_id = 1;  -- Returns 5 rows
T2: INSERT INTO orders (user_id, ...) VALUES (1, ...); COMMIT;
T1: SELECT * FROM orders WHERE user_id = 1;  -- Returns 6 rows!
```
**Prevented by**: SERIALIZABLE (or REPEATABLE READ in MySQL with gap locks)

### 4. Lost Update
```
T1: SELECT balance FROM accounts WHERE id = 1;  -- 100
T2: SELECT balance FROM accounts WHERE id = 1;  -- 100
T1: UPDATE accounts SET balance = 150 WHERE id = 1;  -- 100 + 50
T2: UPDATE accounts SET balance = 120 WHERE id = 1;  -- 100 + 20 (overwrites T1!)
```
**Prevented by**: Optimistic locking, SELECT FOR UPDATE, SERIALIZABLE

## Locking — Controlling Concurrency

### Row Locks

```sql
-- SELECT FOR UPDATE: Lock rows for update (prevents other writes)
START TRANSACTION;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
-- Other transactions: WAIT or ERROR on UPDATE/DELETE/SELECT FOR UPDATE
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;

-- SELECT FOR SHARE: Lock for read (allows other reads, blocks writes)
SELECT * FROM accounts WHERE id = 1 FOR SHARE;

-- NOWAIT / SKIP LOCKED (MySQL 8.0+, PostgreSQL)
SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;        -- Error if locked
SELECT * FROM accounts WHERE id = 1 FOR UPDATE SKIP LOCKED;   -- Skip locked rows
```

### Table Locks (Avoid in OLTP)

```sql
-- MySQL
LOCK TABLES accounts WRITE, orders READ;
-- ... operations ...
UNLOCK TABLES;

-- PostgreSQL
LOCK TABLE accounts IN ACCESS EXCLUSIVE MODE;
-- Only for DDL, bulk loads, maintenance
```

## Deadlocks — Circular Wait

```
T1: Lock A → wants B
T2: Lock B → wants A
→ DEADLOCK!
```

### Detection & Resolution

```sql
-- MySQL: Automatic detection, rolls back one transaction
-- Check deadlock info
SHOW ENGINE INNODB STATUS;

-- PostgreSQL: Automatic, logs in pg_locks
SELECT * FROM pg_locks WHERE NOT granted;
```

### Prevention Strategies

| Strategy | How |
|----------|-----|
| **Consistent lock order** | Always lock tables/rows in same order (e.g., by PK) |
| **Short transactions** | Minimize time holding locks |
| **Avoid user interaction** | No prompts inside transactions |
| **Use indexes** | Row locks instead of table scans |
| **Lower isolation** | READ COMMITTED instead of SERIALIZABLE |

```sql
-- Good: Consistent order by PK
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- Lower ID first
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

-- Bad: Inconsistent order (deadlock prone)
-- T1: UPDATE id=1 then id=2
-- T2: UPDATE id=2 then id=1
```

## Optimistic Locking — Application-Level

```sql
-- Add version column
ALTER TABLE accounts ADD COLUMN version INT DEFAULT 0;

-- Update with version check
UPDATE accounts
SET balance = balance - 100, version = version + 1
WHERE id = 1 AND version = 5;  -- Only succeeds if version still 5

-- Check affected rows
-- 1 row = success, 0 rows = conflict (retry)
```

```sql
-- Alternative: Timestamp
ALTER TABLE accounts ADD COLUMN updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP;

UPDATE accounts
SET balance = balance - 100, updated_at = NOW()
WHERE id = 1 AND updated_at = '2024-01-15 10:30:00';
```

## Distributed Transactions (2PC)

```sql
-- XA Transactions (MySQL, PostgreSQL)
XA START 'xid123';
UPDATE db1.accounts SET balance = balance - 100 WHERE id = 1;
UPDATE db2.accounts SET balance = balance + 100 WHERE id = 2;
XA END 'xid123';
XA PREPARE 'xid123';  -- All participants vote YES
XA COMMIT 'xid123';   -- Coordinator commits
-- Or: XA ROLLBACK 'xid123';
```

> **Note**: 2PC is complex, slow. Prefer saga pattern (choreography/orchestration) for microservices.
