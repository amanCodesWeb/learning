# RIGHT JOIN & FULL JOIN

Less common but useful in specific scenarios. `RIGHT JOIN` mirrors `LEFT JOIN`. `FULL JOIN` combines both.

---

## RIGHT JOIN — Mirror of LEFT JOIN

Returns all rows from the **right** table, matching left rows or NULL.

```sql
-- These are equivalent (just swap table order):
SELECT * FROM users u LEFT JOIN orders o ON u.id = o.user_id;
SELECT * FROM orders o RIGHT JOIN users u ON u.id = o.user_id;
```

### Visual

```
TABLE A (users)          TABLE B (orders)          RIGHT JOIN RESULT
┌────┬────────┐          ┌────┬────────┬────────┐  ┌────┬────────┬────────┐
│ id │ name   │          │ id │ user_id │ total  │  │ id │ name   │ total  │
├────┼────────┤          ├────┼─────────┼────────┤  ├────┼────────┼────────┤
│ 1  │ Alice  │    ──┐   │ 101│ 1       │ 99.99  │  │ 1  │ Alice  │ 99.99  │
│ 2  │ Bob    │  ──┐ │   │ 102│ 1       │ 149.50 │  │ 1  │ Alice  │ 149.50 │
│ 3  │ Carol  │  │ └─┼──►│ 103│ 2       │ 75.00  │  │ 2  │ Bob    │ 75.00  │
│ 4  │ Dave   │  │    │   │ 104│ 5       │ 200.00 │  │ 5  │ NULL   │ 200.00 │
└────┴────────┘  │    │   └────┴────────┴────────┘  └────┴────────┴────────┘
   (no orders)  │    │      (user 5 doesn't exist)
                └────┘
```

**Result**: All 4 orders. Orders 101-103 matched to users. Order 104 has NULL user (user 5 doesn't exist). Carol & Dave excluded (no orders).

## When to Use RIGHT JOIN

### 1. Readability: Start from the "detail" table
```sql
-- You're thinking from orders perspective
SELECT o.id, o.total, u.full_name
FROM orders AS o
RIGHT JOIN users AS u ON o.user_id = u.id;
-- vs
SELECT u.full_name, o.id, o.total
FROM users AS u
LEFT JOIN orders AS o ON u.id = o.user_id;
```

### 2. Multiple LEFT JOINs then a RIGHT JOIN
```sql
-- Complex query where right table is the anchor
SELECT ...
FROM a
LEFT JOIN b ON ...
LEFT JOIN c ON ...
RIGHT JOIN d ON ...  -- d is the primary focus
```

> **Best Practice**: Prefer `LEFT JOIN` — it's more readable (reads top-to-bottom). Use `RIGHT JOIN` only when it genuinely clarifies intent.

## FULL JOIN — All Rows from Both Tables

Returns matches + left-only + right-only. Essentially `LEFT JOIN UNION RIGHT JOIN`.

```sql
-- MySQL: Not supported directly (use UNION)
SELECT * FROM users u LEFT JOIN orders o ON u.id = o.user_id
UNION
SELECT * FROM users u RIGHT JOIN orders o ON u.id = o.user_id;

-- PostgreSQL, SQL Server, Oracle: Native support
SELECT * FROM users u FULL JOIN orders o ON u.id = o.user_id;
-- Or: FULL OUTER JOIN
```

### Visual

```
FULL JOIN RESULT
┌────┬────────┬────────┐
│ id │ name   │ total  │
├────┼────────┼────────┤
│ 1  │ Alice  │ 99.99  │
│ 1  │ Alice  │ 149.50 │
│ 2  │ Bob    │ 75.00  │
│ 3  │ Carol  │ NULL   │  ← User only
│ 4  │ Dave   │ NULL   │  ← User only
│ 5  │ NULL   │ 200.00 │  ← Order only (orphan)
└────┴────────┴────────┘
```

## FULL JOIN Use Cases

### 1. Data Reconciliation / Audit
```sql
-- Find mismatches between two systems
SELECT
    COALESCE(local.id, remote.id) AS id
    , local.email AS local_email
    , remote.email AS remote_email
    , CASE
        WHEN local.id IS NULL THEN 'Only in remote'
        WHEN remote.id IS NULL THEN 'Only in local'
        WHEN local.email != remote.email THEN 'Email mismatch'
        ELSE 'Match'
      END AS status
FROM local_users AS local
FULL JOIN remote_users AS remote ON local.id = remote.id
WHERE local.email != remote.email
   OR local.id IS NULL
   OR remote.id IS NULL;
```

### 2. Time Series with Gaps
```sql
-- All dates in range, with data or NULL
WITH all_dates AS (
    SELECT generate_series('2024-01-01'::date, '2024-12-31'::date, '1 day')::date AS dt
)
SELECT
    d.dt
    , COALESCE(SUM(o.total), 0) AS daily_revenue
FROM all_dates d
LEFT JOIN orders o ON DATE(o.created_at) = d.dt
GROUP BY d.dt
ORDER BY d.dt;

-- With FULL JOIN (if you have two metrics tables)
SELECT
    COALESCE(r.date, s.date) AS date
    , r.revenue
    , s.sessions
FROM revenue_daily r
FULL JOIN sessions_daily s ON r.date = s.date
ORDER BY date;
```

### 3. Schema Comparison
```sql
-- Compare columns between two tables
SELECT
    COALESCE(t1.column_name, t2.column_name) AS column_name
    , t1.data_type AS type_table1
    , t2.data_type AS type_table2
FROM info_schema_columns t1
FULL JOIN info_schema_columns t2
    ON t1.column_name = t2.column_name
    AND t1.table_name = 'users'
    AND t2.table_name = 'users_backup'
WHERE t1.data_type != t2.data_type
   OR t1.column_name IS NULL
   OR t2.column_name IS NULL;
```

## MySQL: Simulating FULL JOIN

```sql
-- Method 1: UNION of LEFT + RIGHT (removes exact duplicates)
SELECT * FROM users u LEFT JOIN orders o ON u.id = o.user_id
UNION
SELECT * FROM users u RIGHT JOIN orders o ON u.id = o.user_id;

-- Method 2: UNION ALL + filter (keeps duplicates if any)
SELECT * FROM users u LEFT JOIN orders o ON u.id = o.user_id
UNION ALL
SELECT * FROM users u RIGHT JOIN orders o ON u.id = o.user_id
WHERE u.id IS NULL;  -- Only right-only rows from second part
```

## CROSS JOIN — Cartesian Product

Every row from A × every row from B. **No ON clause**.

```sql
-- Explicit syntax
SELECT * FROM colors CROSS JOIN sizes;

-- Implicit (old syntax, avoid)
SELECT * FROM colors, sizes;

-- With WHERE (becomes INNER JOIN)
SELECT * FROM colors c, sizes s WHERE c.id = s.color_id;
```

### Visual

```
COLORS (3)     SIZES (3)      CROSS JOIN (9)
┌─────┐        ┌─────┐        ┌─────┬─────┐
│ Red │   ×    │ S   │   =    │ Red │ S   │
│ Blu │        │ M   │        │ Red │ M   │
│ Grn │        │ L   │        │ Red │ L   │
└─────┘        └─────┘        │ Blu │ S   │
                              │ Blu │ M   │
                              │ Blu │ L   │
                              │ Grn │ S   │
                              │ Grn │ M   │
                              └─────┴─────┘
```

### Practical Uses

```sql
-- 1. Generate all combinations (date × product for reporting)
SELECT d.dt, p.id AS product_id
FROM (
    SELECT generate_series('2024-01-01', '2024-12-31', '1 day')::date AS dt
) d
CROSS JOIN products p;

-- 2. Create test data
INSERT INTO user_preferences (user_id, category_id, enabled)
SELECT u.id, c.id, TRUE
FROM users u
CROSS JOIN categories c
WHERE u.is_active = TRUE;

-- 3. Matrix/heatmap data
SELECT
    u.city AS user_city
    , s.city AS store_city
    , COUNT(*) AS interactions
FROM users u
CROSS JOIN stores s
LEFT JOIN interactions i ON u.id = i.user_id AND s.id = i.store_id
GROUP BY u.city, s.city;
```

> **⚠️ Warning**: CROSS JOIN on large tables = massive result (1M × 1M = 1 trillion rows). Always use with small tables or LIMIT.

---

## NATURAL JOIN — Avoid

Joins on **all columns with same name**. Dangerous — schema changes break queries silently.

```sql
-- ❌ Avoid: fragile, implicit
SELECT * FROM users NATURAL JOIN orders;
-- Joins on ALL same-name columns (id, created_at, etc.)

-- ✅ Explicit: clear, stable
SELECT * FROM users u JOIN orders o ON u.id = o.user_id;
```

## Join Type Quick Reference

| Join | Returns | Use When |
|------|---------|----------|
| `INNER JOIN` | Matches only | Both sides must exist |
| `LEFT JOIN` | All left + matches | Primary table = left, optional right |
| `RIGHT JOIN` | All right + matches | Primary table = right (rare) |
| `FULL JOIN` | All from both | Reconciliation, merging datasets |
| `CROSS JOIN` | All combinations | Generating matrices, test data |
