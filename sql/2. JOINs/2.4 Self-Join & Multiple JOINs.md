# Self-Join & Multiple JOINs

A **self-join** is joining a table to itself. **Multiple JOINs** chain several tables together. Both are essential for real-world queries.

---

## Self-Join — Table Joined to Itself

Use when a table has a **hierarchical** or **recursive** relationship.

```sql
-- Employees table with manager_id referencing same table
CREATE TABLE employees (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    role VARCHAR(50),
    manager_id INT,
    FOREIGN KEY (manager_id) REFERENCES employees(id)
);

-- Self-join: Employee → Manager
SELECT
    e.name AS employee
    , e.role AS emp_role
    , m.name AS manager
    , m.role AS mgr_role
FROM employees AS e
LEFT JOIN employees AS m ON e.manager_id = m.id;
```

## Self-Join Patterns

### 1. Hierarchy Traversal (Adjacency List)

```sql
-- Direct reports only
SELECT m.name AS manager, e.name AS report
FROM employees e
JOIN employees m ON e.manager_id = m.id;

-- Full path (recursive CTE - see Module 4)
WITH RECURSIVE hierarchy AS (
    SELECT id, name, manager_id, 1 AS level, name::text AS path
    FROM employees WHERE manager_id IS NULL
    UNION ALL
    SELECT e.id, e.name, e.manager_id, h.level + 1, h.path || ' > ' || e.name
    FROM employees e JOIN hierarchy h ON e.manager_id = h.id
)
SELECT * FROM hierarchy ORDER BY path;
```

### 2. Peer Comparison (Same Table, Different Rows)

```sql
-- Products in same category, different price
SELECT
    p1.name AS product_a
    , p1.price AS price_a
    , p2.name AS product_b
    , p2.price AS price_b
    , p1.price - p2.price AS diff
FROM products p1
JOIN products p2
    ON p1.category_id = p2.category_id
    AND p1.id < p2.id  -- Avoid duplicates (A-B and B-A) and self-pair
WHERE ABS(p1.price - p2.price) < 50;
```

### 3. Find Duplicates

```sql
-- Users with same email (data quality check)
SELECT u1.id, u1.email, u2.id AS duplicate_id
FROM users u1
JOIN users u2
    ON u1.email = u2.email
    AND u1.id < u2.id;
```

### 4. Time-Series Self-Join (Period-over-Period)

```sql
-- Month-over-month revenue comparison
SELECT
    curr.month
    , curr.revenue AS this_month
    , prev.revenue AS last_month
    , curr.revenue - prev.revenue AS change
    , ROUND((curr.revenue - prev.revenue) / prev.revenue * 100, 1) AS pct_change
FROM monthly_revenue curr
LEFT JOIN monthly_revenue prev
    ON curr.month = DATE_ADD(prev.month, INTERVAL 1 MONTH);
```

## Multiple JOINs — Chaining Tables

Real queries often join 4-10+ tables. Key principles:

### 1. Join Order (Logical, Not Physical)

```sql
-- Logical flow: start from the "anchor" table
SELECT
    u.full_name AS customer
    , o.id AS order_id
    , o.created_at
    , oi.quantity
    , p.name AS product
    , p.brand
    , cat.name AS category
    , oi.unit_price
    , oi.total AS line_total
    , pm.name AS payment_method
    , sh.address AS shipping_address
FROM users AS u                    -- Anchor: who
INNER JOIN orders AS o ON u.id = o.user_id
INNER JOIN order_items AS oi ON o.id = oi.order_id
INNER JOIN products AS p ON oi.product_id = p.id
INNER JOIN categories AS cat ON p.category_id = cat.id
LEFT JOIN payments AS pm ON o.id = pm.order_id
LEFT JOIN addresses AS sh ON o.shipping_address_id = sh.id
WHERE u.is_active = TRUE
    AND o.status = 'delivered'
ORDER BY o.created_at DESC;
```

### 2. Join Order Affects Performance

```sql
-- ❌ Bad: Large table first, filters late
SELECT * FROM huge_logs h
JOIN small_users u ON h.user_id = u.id
WHERE u.country = 'USA';

-- ✅ Good: Filter early, join small first
SELECT * FROM small_users u
JOIN huge_logs h ON u.id = h.user_id
WHERE u.country = 'USA';
-- Or let optimizer handle it (modern DBs do this well)
```

### 3. Mixed JOIN Types

```sql
-- Core path: INNER JOIN (required relationships)
-- Optional path: LEFT JOIN (may not exist)

SELECT
    u.full_name
    , o.id AS order_id
    , o.total
    , pm.provider AS payment_provider  -- May be NULL
    , sh.city AS ship_city              -- May be NULL
    , c.name AS coupon_code             -- May be NULL
FROM users u
INNER JOIN orders o ON u.id = o.user_id           -- Every order has user
LEFT JOIN payments pm ON o.id = pm.order_id       -- Payment optional
LEFT JOIN addresses sh ON o.shipping_address_id = sh.id  -- Address optional
LEFT JOIN coupons c ON o.coupon_id = c.id         -- Coupon optional
WHERE u.is_active = TRUE;
```

## Multiple JOIN Performance Tips

### 1. Index Every Foreign Key

```sql
-- Essential indexes for JOIN performance
CREATE INDEX idx_orders_user_id ON orders(user_id);
CREATE INDEX idx_order_items_order_id ON order_items(order_id);
CREATE INDEX idx_order_items_product_id ON order_items(product_id);
CREATE INDEX idx_products_category_id ON products(category_id);
CREATE INDEX idx_payments_order_id ON payments(order_id);
```

### 2. Composite Indexes for Filtered JOINs

```sql
-- Query: WHERE u.country='USA' AND o.status='delivered'
-- Index supports both filter and join
CREATE INDEX idx_orders_user_status ON orders(user_id, status);
CREATE INDEX idx_users_country ON users(country);
```

### 3. Reduce Rows Early

```sql
-- ❌ Join first, filter later (more rows processed)
SELECT * FROM users u
JOIN orders o ON u.id = o.user_id
JOIN order_items oi ON o.id = oi.order_id
WHERE u.country = 'USA' AND o.status = 'delivered';

-- ✅ Filter in CTE/subquery first, then join
WITH filtered_orders AS (
    SELECT * FROM orders
    WHERE status = 'delivered'
      AND user_id IN (SELECT id FROM users WHERE country = 'USA')
)
SELECT * FROM users u
JOIN filtered_orders o ON u.id = o.user_id
JOIN order_items oi ON o.id = oi.order_id;
```

### 4. Use EXPLAIN to Verify

```sql
EXPLAIN
SELECT u.name, o.total
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE u.country = 'USA';

-- Look for:
-- - "type": ref, eq_ref (good) vs ALL (bad - full scan)
-- - "key": index name being used
-- - "rows": estimated rows examined (should be small)
```

## Common Multiple JOIN Patterns

### 1. Star Schema (Fact + Dimensions)
```sql
-- Fact table: orders
-- Dimensions: users, products, dates, stores
SELECT
    d.date
    , u.city AS customer_city
    , s.city AS store_city
    , p.category
    , SUM(f.total) AS revenue
FROM fact_orders f
JOIN dim_users u ON f.user_id = u.id
JOIN dim_products p ON f.product_id = p.id
JOIN dim_dates d ON f.date_id = d.id
JOIN dim_stores s ON f.store_id = s.id
GROUP BY d.date, u.city, s.city, p.category;
```

### 2. Bridge Table (Many-to-Many)
```sql
-- Products ↔ Tags
SELECT p.name, GROUP_CONCAT(t.name) AS tags
FROM products p
JOIN product_tags pt ON p.id = pt.product_id
JOIN tags t ON pt.tag_id = t.id
GROUP BY p.id, p.name;
```

### 3. Polymorphic Association (Single Table, Multiple Parents)
```sql
-- Comments on: products, orders, blog_posts
SELECT c.*, 'product' AS type, p.name AS parent
FROM comments c JOIN products p ON c.commentable_id = p.id AND c.commentable_type = 'product'
UNION ALL
SELECT c.*, 'order' AS type, o.id AS parent
FROM comments c JOIN orders o ON c.commentable_id = o.id AND c.commentable_type = 'order'
UNION ALL
SELECT c.*, 'post' AS type, bp.title AS parent
FROM comments c JOIN blog_posts bp ON c.commentable_id = bp.id AND c.commentable_type = 'post';
```

## JOIN Troubleshooting Checklist

| Symptom | Likely Cause | Fix |
|---------|--------------|-----|
| Too many rows | Missing join condition / Cartesian product | Add ON clause, check FK |
| Too few rows | INNER JOIN excluding NULLs | Use LEFT JOIN |
| NULLs where data expected | LEFT JOIN but WHERE filters right table | Move condition to ON |
| Slow query | Missing indexes on FK columns | Add indexes, check EXPLAIN |
| Duplicate rows | One-to-many without DISTINCT/GROUP BY | Aggregate or DISTINCT |
| Ambiguous column error | Same column name in multiple tables | Use table aliases, qualify columns |
