# ORDER BY — Sorting Results

`ORDER BY` controls the sequence of returned rows. Without it, order is **not guaranteed** — even if it looks consistent.

---

## Basic Syntax

```sql
SELECT column1, column2, ...
FROM table_name
[WHERE condition]
ORDER BY column1 [ASC|DESC], column2 [ASC|DESC], ...;
```

- `ASC` = Ascending (default): A→Z, 0→9, oldest→newest
- `DESC` = Descending: Z→A, 9→0, newest→oldest

---

## Single Column Sorting

```sql
-- Ascending (default)
SELECT * FROM products ORDER BY price;
SELECT * FROM products ORDER BY price ASC;

-- Descending
SELECT * FROM products ORDER BY price DESC;

-- By alias
SELECT name, price * 1.1 AS price_with_tax
FROM products
ORDER BY price_with_tax DESC;

-- By column position (avoid: fragile if SELECT changes)
SELECT name, price FROM products ORDER BY 2 DESC;
```

---

## Multi-Column Sorting

```sql
-- Primary: category ASC, Secondary: price DESC
SELECT * FROM products
ORDER BY category ASC, price DESC;

-- Users: active first, then newest
SELECT * FROM users
ORDER BY is_active DESC, created_at DESC;

-- Orders: status priority, then date
SELECT * FROM orders
ORDER BY
    CASE status
        WHEN 'pending' THEN 1
        WHEN 'paid' THEN 2
        WHEN 'shipped' THEN 3
        WHEN 'delivered' THEN 4
        WHEN 'cancelled' THEN 5
    END,
    created_at DESC;
```

---

## NULL Handling in Sorting

```sql
-- Default: NULLs first (MySQL, SQLite) or last (PostgreSQL, SQL Server)
SELECT * FROM users ORDER BY phone;  -- NULLs appear first in MySQL

-- Explicit control (PostgreSQL, Oracle, SQL Server)
ORDER BY phone NULLS FIRST;
ORDER BY phone NULLS LAST;

-- MySQL workaround: use IS NULL in ORDER BY
ORDER BY (phone IS NULL), phone;     -- NULLs last
ORDER BY (phone IS NOT NULL), phone; -- NULLs first

-- Universal: COALESCE to a sort value
ORDER BY COALESCE(phone, 'zzz');     -- NULLs sort as 'zzz' (last for strings)
ORDER BY COALESCE(sort_order, 9999); -- NULLs sort as 9999 (last for numbers)
```

## Sorting by Computed Expressions

```sql
-- Sort by profit margin
SELECT name, price, cost, (price - cost) AS profit
FROM products
ORDER BY profit DESC;

-- Sort by string length
SELECT name FROM products ORDER BY LENGTH(name);

-- Sort by date part
SELECT * FROM orders ORDER BY MONTH(created_at), DAY(created_at);

-- Sort by custom priority
SELECT * FROM tickets
ORDER BY
    CASE priority
        WHEN 'critical' THEN 1
        WHEN 'high' THEN 2
        WHEN 'medium' THEN 3
        WHEN 'low' THEN 4
    END;
```

## ORDER BY with LIMIT — Critical for Pagination

```sql
-- ❌ Without ORDER BY: unpredictable which 10 rows you get
SELECT * FROM users LIMIT 10;

-- ✅ With ORDER BY: consistent, predictable pages
SELECT * FROM users ORDER BY created_at DESC LIMIT 10;

-- Page 2 (OFFSET 10)
SELECT * FROM users ORDER BY created_at DESC LIMIT 10 OFFSET 10;
```

> **Rule**: **Always use ORDER BY with LIMIT**. Without it, pagination is broken.

## Performance: Indexes & ORDER BY

```sql
-- This query can use an index on (is_active, created_at)
SELECT * FROM users
WHERE is_active = TRUE
ORDER BY created_at DESC
LIMIT 20;

-- This CANNOT use index efficiently (mixed ASC/DESC)
SELECT * FROM users
WHERE is_active = TRUE
ORDER BY created_at ASC, updated_at DESC;

-- Composite index must match ORDER BY direction
-- For: ORDER BY a ASC, b DESC
-- Need index: (a ASC, b DESC)  -- MySQL 8.0+, PostgreSQL
```

| Scenario | Can Use Index? |
|----------|----------------|
| `WHERE a=1 ORDER BY b` | Yes, if index on (a, b) |
| `WHERE a=1 ORDER BY b DESC` | Yes, if index on (a, b DESC) |
| `ORDER BY a, b` | Yes, if index on (a, b) |
| `ORDER BY a ASC, b DESC` | Only with DESC index support |
| `ORDER BY RAND()` | **Never** — full table scan |
| `ORDER BY column NOT IN INDEX` | Filesort (slow on large tables) |

## Random Ordering (Sampling)

```sql
-- MySQL / PostgreSQL / SQLite
SELECT * FROM users ORDER BY RAND() LIMIT 5;
SELECT * FROM users ORDER BY RANDOM() LIMIT 5;

-- PostgreSQL: TABLESAMPLE (fast, approximate)
SELECT * FROM users TABLESAMPLE BERNOULLI (10);  -- ~10% of rows

-- Large tables: avoid ORDER BY RAND() — use this instead
-- Get random offset, then LIMIT
SET @skip = FLOOR(RAND() * (SELECT COUNT(*) FROM users));
PREPARE stmt FROM 'SELECT * FROM users LIMIT 1 OFFSET ?';
EXECUTE stmt USING @skip;
```

## Collation & Locale-Aware Sorting

```sql
-- MySQL: specify collation for sorting
SELECT * FROM users ORDER BY name COLLATE utf8mb4_unicode_ci;

-- German: ä = ae, ö = oe, ü = ue, ß = ss
SELECT * FROM users ORDER BY name COLLATE utf8mb4_german2_ci;

-- PostgreSQL: use ICU collations
SELECT * FROM users ORDER BY name COLLATE "de-DE-x-icu";

-- Case-sensitive sort (uppercase before lowercase)
SELECT * FROM users ORDER BY name COLLATE utf8mb4_bin;
```

## Common Mistakes

| Mistake | Problem | Fix |
|---------|---------|-----|
| No ORDER BY with LIMIT | Random pagination | Always ORDER BY |
| ORDER BY column position | Breaks when SELECT changes | Use column name/alias |
| `ORDER BY RAND()` on large table | Full scan, very slow | Use alternative sampling |
| Mixed ASC/DESC without proper index | Filesort | Create matching composite index |
| Assuming default NULL order | Differs by database | Explicit NULLS FIRST/LAST or COALESCE |
