# LIMIT & Pagination

`LIMIT` restricts the number of rows returned. Combined with `OFFSET`, it enables pagination. But large offsets are slow — there are better approaches.

---

## Basic Syntax

```sql
-- First N rows
SELECT * FROM users LIMIT 10;

-- Skip M rows, take N rows (pagination)
SELECT * FROM users LIMIT 10 OFFSET 20;  -- Page 3, 10 per page

-- MySQL shorthand
SELECT * FROM users LIMIT 20, 10;  -- OFFSET 20, LIMIT 10
```

---

## Pagination Patterns

### 1. Offset Pagination (Simple, Slow at Scale)

```sql
-- Page 1
SELECT * FROM products ORDER BY created_at DESC LIMIT 20 OFFSET 0;

-- Page 2
SELECT * FROM products ORDER BY created_at DESC LIMIT 20 OFFSET 20;

-- Page N
SELECT * FROM products ORDER BY created_at DESC LIMIT 20 OFFSET (page-1)*20;
```

| Pros | Cons |
|------|------|
| Simple to implement | **Slow for deep pages** (scans skipped rows) |
| Easy to jump to page N | Inconsistent if data changes between pages |
| Works with any ORDER BY | Offset 1,000,000 = scan 1M rows |

### 2. Keyset Pagination (Seek Method) — **Recommended**

```sql
-- Instead of OFFSET, remember the last row's sort key
-- Page 1: Get first 20
SELECT * FROM products
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- Page 2: Use last row's values as cursor
-- Last row: created_at='2024-01-15 10:30:00', id=1234
SELECT * FROM products
WHERE (created_at, id) < ('2024-01-15 10:30:00', 1234)
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- Works with single column too
SELECT * FROM products
WHERE created_at < '2024-01-15 10:30:00'
ORDER BY created_at DESC
LIMIT 20;
```

| Pros | Cons |
|------|------|
| **Constant fast performance** (uses index) | Can't jump to arbitrary page N |
| Consistent results if data changes | Requires unique, stable sort key |
| Works at any scale | Slightly more complex client logic |

> **Why it works**: Database seeks directly to the position using the index, instead of scanning and discarding OFFSET rows.

### 3. Cursor-Based Pagination (API Friendly)

```sql
-- Encode cursor as base64 JSON: {"created_at":"2024-01-15T10:30:00Z","id":1234}
-- Decode on next request

-- First request (no cursor)
SELECT id, name, created_at
FROM products
ORDER BY created_at DESC, id DESC
LIMIT 21;  -- Fetch 21 to detect if more pages exist

-- Subsequent requests
SELECT id, name, created_at
FROM products
WHERE (created_at, id) < (:cursor_created_at, :cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT 21;

-- Response includes: data[0..19], next_cursor from data[20] if 21 rows returned
```

## LIMIT Variants by Database

| Database | Syntax |
|----------|--------|
| MySQL, PostgreSQL, SQLite | `LIMIT n OFFSET m` |
| MySQL (alt) | `LIMIT m, n` |
| SQL Server / Oracle 12c+ | `OFFSET m ROWS FETCH NEXT n ROWS ONLY` |
| Oracle 11g | `ROWNUM` subquery (complex) |

## Performance Comparison

```sql
-- Table: 1,000,000 rows, indexed on created_at

-- OFFSET 0 (page 1) - Fast
EXPLAIN SELECT * FROM logs ORDER BY created_at DESC LIMIT 20;
-- → Index scan, stops after 20 rows

-- OFFSET 500,000 (page 25,000) - SLOW
EXPLAIN SELECT * FROM logs ORDER BY created_at DESC LIMIT 20 OFFSET 500000;
-- → Index scan, reads 500,020 rows, discards 500,000

-- Keyset pagination - Fast at any depth
EXPLAIN SELECT * FROM logs
WHERE created_at < '2023-06-15'
ORDER BY created_at DESC LIMIT 20;
-- → Index seek, reads ~20 rows
```

## Counting Total Rows (For Page Counts)

```sql
-- Simple but slow on large tables
SELECT COUNT(*) FROM products WHERE category = 'Laptops';

-- Faster: approximate count (PostgreSQL)
SELECT reltuples::bigint AS estimate
FROM pg_class
WHERE relname = 'products';

-- Faster: cached count (application level)
-- Store count in Redis, update on write

-- MySQL: use EXPLAIN for quick estimate
EXPLAIN SELECT * FROM products WHERE category = 'Laptops';
-- Look at "rows" estimate in output
```

> **Tip**: For UIs showing "Page 1 of 50", consider:
> - Show "Load More" instead of page numbers (keyset pagination)
> - Cache total count, update asynchronously
> - Use approximate counts for huge tables

## LIMIT in Subqueries

```sql
-- Top 5 customers by spending
SELECT * FROM (
    SELECT user_id, SUM(total) AS lifetime_value
    FROM orders
    GROUP BY user_id
    ORDER BY lifetime_value DESC
    LIMIT 5
) AS top_customers
JOIN users u ON top_customers.user_id = u.id;

-- Per-group limit (top N per category) — MySQL 8.0+ / PostgreSQL
SELECT * FROM (
    SELECT *,
        ROW_NUMBER() OVER (PARTITION BY category ORDER BY price DESC) AS rn
    FROM products
) AS ranked
WHERE rn <= 3;
```

## Common Mistakes

| Mistake | Problem | Fix |
|---------|---------|-----|
| `LIMIT` without `ORDER BY` | Unpredictable results | Always pair with `ORDER BY` |
| Large `OFFSET` | Linear slowdown | Use keyset pagination |
| `OFFSET` in subquery | Optimizer may not optimize | Rewrite as JOIN or CTE |
| Fetching `COUNT(*)` every request | Slow on large tables | Cache or approximate |
| Not using unique tiebreaker in keyset | Duplicate/missing rows at boundaries | Always include PK in ORDER BY |
