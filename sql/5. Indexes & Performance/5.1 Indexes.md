# Indexes — Making Queries Fast

Indexes are data structures that speed up data retrieval. Like a book index — find pages without scanning every page.

---

## How Indexes Work

```
WITHOUT INDEX (Full Table Scan)          WITH INDEX (B-Tree)
┌─────────────────────────────┐          ┌─────────────────────────────┐
│ id │ name  │ email           │          │          Root Node          │
├────┼───────┼─────────────────┤          │        [M, S]               │
│ 1  │ Alice │ alice@...       │          │         /   \               │
│ 2  │ Bob   │ bob@...         │          │      [G]     [T]            │
│ 3  │ Carol │ carol@...       │          │     /  \    /  \            │
│ ...│ ...   │ ...             │          │  [A] [K] [P] [Z]  ← Leaf    │
│ N  │ Zoe   │ zoe@...         │          │                              │
└────┴───────┴─────────────────┘          └─────────────────────────────┘
Scan all N rows                              Log₂(N) lookups (~3 for 1M rows)
```

---

## Index Types

| Type | Structure | Best For | Databases |
|------|-----------|----------|-----------|
| **B-Tree** | Balanced tree | Equality, range, sorting | All (default) |
| **Hash** | Hash table | Exact equality only | MySQL (MEMORY), PostgreSQL |
| **GiST/GIN** | Generalized trees | Full-text, JSON, geo | PostgreSQL |
| **Full-text** | Inverted index | Text search | MySQL, PostgreSQL, SQL Server |
| **Spatial** | R-tree | Geometry/geography | PostgreSQL (PostGIS), MySQL |
| **Bitmap** | Bit vectors | Low cardinality, DW | Oracle, PostgreSQL (via extension) |

## Creating Indexes

```sql
-- Single column
CREATE INDEX idx_users_email ON users(email);

-- Composite (multiple columns) — ORDER MATTERS!
CREATE INDEX idx_orders_user_status ON orders(user_id, status);

-- Unique index (enforces uniqueness + speeds up lookup)
CREATE UNIQUE INDEX idx_users_email ON users(email);

-- Partial index (PostgreSQL, SQLite, SQL Server) — only index subset
CREATE INDEX idx_active_users ON users(email) WHERE is_active = TRUE;

-- Covering index (include non-key columns) — PostgreSQL 11+, SQL Server
CREATE INDEX idx_orders_user_total ON orders(user_id) INCLUDE (total, status);

-- Functional index (index on expression)
CREATE INDEX idx_users_lower_email ON users(LOWER(email));
CREATE INDEX idx_orders_month ON orders(DATE_TRUNC('month', created_at));
```

## Composite Index Column Order — Critical!

```sql
-- Query: WHERE user_id = 1 AND status = 'delivered'
-- Index: (user_id, status)  ✅ Perfect match
-- Index: (status, user_id)  ❌ Can use status, but user_id not selective

-- Rule: Equality columns FIRST, then range/sort columns
-- WHERE a = 1 AND b = 2 AND c > 3 ORDER BY d
-- Best index: (a, b, c, d) or (a, b, d, c)
```

### The "Leftmost Prefix" Rule

```sql
-- Index: (a, b, c)

-- ✅ Uses index: WHERE a = 1
-- ✅ Uses index: WHERE a = 1 AND b = 2
-- ✅ Uses index: WHERE a = 1 AND b = 2 AND c = 3
-- ✅ Uses index: WHERE a = 1 ORDER BY b, c

-- ❌ Full scan: WHERE b = 2 (no leading column)
-- ❌ Partial: WHERE a = 1 AND c = 3 (skips b, can't use c efficiently)
-- ⚠️ Partial: WHERE a = 1 ORDER BY c (can use a, but filesort on c)
```

## When Indexes Help

| Query Pattern | Index Helps? |
|---------------|--------------|
| `WHERE col = value` | ✅ Yes |
| `WHERE col > value` | ✅ Yes (range) |
| `WHERE col BETWEEN x AND y` | ✅ Yes |
| `WHERE col IN (1,2,3)` | ✅ Yes |
| `WHERE col LIKE 'prefix%'` | ✅ Yes |
| `WHERE col LIKE '%suffix'` | ❌ No (leading wildcard) |
| `WHERE func(col) = value` | ❌ No (unless functional index) |
| `ORDER BY col` | ✅ Yes |
| `GROUP BY col` | ✅ Yes |
| `JOIN ON a.col = b.col` | ✅ Yes (on FK) |

---

## When Indexes Hurt

| Scenario | Why |
|----------|-----|
| **Small tables** (< 1000 rows) | Full scan faster than index lookup |
| **Low selectivity** (boolean, gender) | Returns >20% rows, scan faster |
| **Frequent writes** (INSERT/UPDATE/DELETE) | Every write updates all indexes |
| **Wide indexes** (many columns, long strings) | Large index size, more I/O |
| **Unused indexes** | Waste space, slow writes |

## Index Maintenance

```sql
-- View indexes
-- MySQL
SHOW INDEX FROM users;
-- PostgreSQL
\d users
-- Or:
SELECT * FROM pg_indexes WHERE tablename = 'users';

-- Drop index
DROP INDEX idx_users_email ON users;  -- MySQL
DROP INDEX idx_users_email;           -- PostgreSQL

-- Rebuild (defragment)
-- MySQL
OPTIMIZE TABLE users;
-- Or: ALTER TABLE users ENGINE=InnoDB;
-- PostgreSQL
REINDEX TABLE users;
-- Or: REINDEX INDEX idx_users_email;
```

## Analyzing Query Plans — EXPLAIN

```sql
-- MySQL
EXPLAIN SELECT * FROM users WHERE email = 'alice@example.com';
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'alice@example.com';  -- 8.0+

-- PostgreSQL
EXPLAIN SELECT * FROM users WHERE email = 'alice@example.com';
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'alice@example.com';  -- Actual times
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) ...  -- Detailed
```

### Key EXPLAIN Output Fields

| Field | Meaning | Good | Bad |
|-------|---------|------|-----|
| `type` / `node_type` | Access method | `ref`, `eq_ref`, `index` | `ALL` (full scan) |
| `key` / `index_name` | Index used | Index name | `NULL` |
| `rows` | Estimated rows examined | Small | Large (near table size) |
| `filtered` | % rows after filter | High (100) | Low |
| `Extra` | Additional info | `Using index` | `Using filesort`, `Using temporary` |

### Common Patterns

```sql
-- ✅ Good: Index lookup
type=ref, key=idx_users_email, rows=1, Extra=Using index

-- ⚠️ Index scan but no table lookup (covering index)
type=index, key=idx_users_email, rows=1000, Extra=Using index

-- ❌ Bad: Full table scan
type=ALL, key=NULL, rows=1000000, Extra=Using where

-- ❌ Bad: Filesort (no index for ORDER BY)
type=ref, key=idx_user_id, rows=500, Extra=Using filesort

-- ❌ Bad: Temporary table (complex GROUP BY)
type=ALL, key=NULL, rows=10000, Extra=Using temporary; Using filesort
```

## Covering Indexes — Avoid Table Lookup

```sql
-- Query only needs indexed columns
SELECT user_id, status FROM orders WHERE user_id = 1;

-- If index is (user_id, status), it's "covering" — no table access!
-- MySQL: Extra=Using index
-- PostgreSQL: Index Only Scan
```

```sql
-- Create covering index explicitly
-- PostgreSQL 11+
CREATE INDEX idx_orders_user_status_total ON orders(user_id, status) INCLUDE (total);

-- MySQL: Include columns in index (makes it wider but covering)
CREATE INDEX idx_orders_user_status_total ON orders(user_id, status, total);
```

## Index Strategy Checklist

### 1. Index All Foreign Keys
```sql
-- Every FK column needs an index
CREATE INDEX idx_orders_user_id ON orders(user_id);
CREATE INDEX idx_order_items_order_id ON order_items(order_id);
CREATE INDEX idx_order_items_product_id ON order_items(product_id);
```

### 2. Index WHERE / JOIN / ORDER BY Columns
```sql
-- Common filters
CREATE INDEX idx_users_email ON users(email);
CREATE INDEX idx_orders_status ON orders(status);
CREATE INDEX idx_orders_created_at ON orders(created_at);

-- Composite for common combinations
CREATE INDEX idx_orders_user_status ON orders(user_id, status);
CREATE INDEX idx_orders_status_date ON orders(status, created_at);
```

### 3. Avoid Redundant Indexes
```sql
-- If you have (a, b), you DON'T need (a) — it's a prefix
-- But you DO need (b) if you query WHERE b = x without a
```

### 4. Monitor Index Usage
```sql
-- MySQL: sys.schema_unused_indexes
SELECT * FROM sys.schema_unused_indexes;

-- PostgreSQL: pg_stat_user_indexes
SELECT indexrelname, idx_scan FROM pg_stat_user_indexes
WHERE idx_scan = 0 AND schemaname = 'public';
```
