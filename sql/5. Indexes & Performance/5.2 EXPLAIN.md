# EXPLAIN & Query Optimization

`EXPLAIN` shows the database's execution plan. Master it to diagnose and fix slow queries.

---

## EXPLAIN Basics

```sql
-- MySQL
EXPLAIN SELECT * FROM users WHERE email = 'alice@example.com';
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'alice@example.com';  -- 8.0+: actual execution

-- PostgreSQL
EXPLAIN SELECT * FROM users WHERE email = 'alice@example.com';
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'alice@example.com';  -- Actual times
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) SELECT ...;  -- Detailed JSON

-- SQL Server
SET STATISTICS IO ON; SET STATISTICS TIME ON;
SELECT ...;  -- Or use SSMS "Include Actual Execution Plan"
```

## MySQL EXPLAIN Output

```sql
EXPLAIN SELECT u.*, o.total
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE u.country = 'USA' AND o.status = 'delivered';
```

| id | select_type | table | partitions | type | possible_keys | key | key_len | ref | rows | filtered | Extra |
|----|-------------|-------|------------|------|---------------|-----|---------|-----|------|----------|-------|
| 1  | SIMPLE      | u     | NULL       | ref  | idx_country   | idx_country | 152 | const | 500 | 100.00 | Using index condition |
| 1  | SIMPLE      | o     | NULL       | ref  | idx_user_status | idx_user_status | 158 | u.id,const | 10 | 100.00 | Using where |

### Key Columns

| Column | Meaning |
|--------|---------|
| `id` | Query block identifier |
| `select_type` | SIMPLE, PRIMARY, SUBQUERY, DERIVED, UNION, etc. |
| `table` | Table name or alias |
| `type` | **Access type** (most important!) |
| `possible_keys` | Indexes that could be used |
| `key` | **Index actually chosen** |
| `key_len` | Bytes of key used |
| `ref` | Columns/constants compared to index |
| `rows` | **Estimated rows examined** |
| `filtered` | % rows remaining after WHERE |
| `Extra` | Additional info (filesort, temporary, etc.) |

---

## Access Types (type) — Best to Worst

| Type | Description | Performance |
|------|-------------|-------------|
| `system` | Table has 0-1 row | Instant |
| `const` | PRIMARY KEY / UNIQUE lookup | Instant |
| `eq_ref` | JOIN on PRIMARY/UNIQUE key | Excellent |
| `ref` | JOIN on non-unique index | Good |
| `fulltext` | Full-text search | Specialized |
| `ref_or_null` | Like ref + NULL handling | Good |
| `index_merge` | Multiple indexes combined | Okay |
| `unique_subquery` | IN (SELECT PK...) | Good |
| `index_subquery` | IN (SELECT indexed...) | Okay |
| `range` | Index range scan (BETWEEN, >, <) | Okay |
| `index` | Full index scan | Slow |
| `ALL` | **Full table scan** | **Worst** |

> **Goal**: Avoid `ALL` and `index` on large tables. Aim for `ref`, `eq_ref`, `range`.

---

## Extra Column — Critical Flags

| Extra Value | Meaning | Action |
|-------------|---------|--------|
| `Using index` | **Covering index** — no table lookup | ✅ Good |
| `Using where` | WHERE filter applied after index | Normal |
| `Using index condition` | Index Condition Pushdown (ICP) | ✅ Good |
| `Using filesort` | **No index for ORDER BY** | ❌ Add index |
| `Using temporary` | **Internal temp table** (GROUP BY/DISTINCT) | ❌ Optimize |
| `Using join buffer` | Block Nested Loop join | ❌ Add index on JOIN column |
| `Select tables optimized away` | COUNT(*) on MyISAM / optimized away | ✅ Good |
| `Impossible WHERE` | Condition always false | Check logic |
| `No tables used` | SELECT without FROM | N/A |

## Common Problems & Fixes

### 1. Full Table Scan (type=ALL)

```sql
-- Problem
EXPLAIN SELECT * FROM orders WHERE status = 'delivered';
-- type=ALL, rows=1000000

-- Fix: Add index
CREATE INDEX idx_orders_status ON orders(status);
-- type=ref, rows=20000
```

### 2. Filesort (Using filesort)

```sql
-- Problem
EXPLAIN SELECT * FROM orders WHERE user_id = 1 ORDER BY created_at DESC;
-- Using filesort

-- Fix: Composite index matching WHERE + ORDER BY
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at DESC);
-- Using index (no filesort)
```

### 3. Temporary Table (Using temporary)

```sql
-- Problem
EXPLAIN SELECT user_id, COUNT(*) FROM orders GROUP BY user_id;
-- Using temporary

-- Fix: Index on GROUP BY column
CREATE INDEX idx_orders_user_id ON orders(user_id);
-- Or: If MySQL 8.0+, hash aggregation may avoid temp table
```

### 4. Join Buffer (Using join buffer)

```sql
-- Problem
EXPLAIN SELECT * FROM users u JOIN orders o ON u.id = o.user_id;
-- Using join buffer (Block Nested Loop)

-- Fix: Index on JOIN column (FK)
CREATE INDEX idx_orders_user_id ON orders(user_id);
-- Becomes ref/eq_ref join
```

### 5. Low Filtered % (Filtered << 100)

```sql
-- Problem
EXPLAIN SELECT * FROM orders WHERE user_id = 1 AND total > 10000;
-- rows=5000, filtered=2.00 (only 2% match total > 10000)

-- Fix: Composite index
CREATE INDEX idx_orders_user_total ON orders(user_id, total);
-- rows=10, filtered=100
```

## Query Optimization Patterns

### 1. Sargable Queries (Search ARGument ABLE)

```sql
-- ❌ Not sargable: function on column
WHERE YEAR(created_at) = 2024
WHERE UPPER(email) = 'ALICE@EXAMPLE.COM'
WHERE created_at + INTERVAL 1 DAY > NOW()

-- ✅ Sargable: column on one side
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01'
WHERE email = 'alice@example.com'  -- With case-insensitive collation
WHERE created_at > DATE_SUB(NOW(), INTERVAL 1 DAY)
```

### 2. Avoid SELECT *

```sql
-- ❌ Reads all columns, prevents covering index
SELECT * FROM orders WHERE user_id = 1;

-- ✅ Only needed columns, enables covering index
SELECT id, total, status FROM orders WHERE user_id = 1;
```

### 3. LIMIT Without ORDER BY

```sql
-- ❌ Unpredictable results
SELECT * FROM orders LIMIT 10;

-- ✅ Deterministic
SELECT * FROM orders ORDER BY created_at DESC LIMIT 10;
```

### 4. OR Conditions

```sql
-- ❌ Hard to optimize
WHERE status = 'paid' OR user_id = 1

-- ✅ UNION (each part uses its index)
SELECT * FROM orders WHERE status = 'paid'
UNION
SELECT * FROM orders WHERE user_id = 1;
```

### 5. Pagination: OFFSET vs Keyset

```sql
-- ❌ Slow for deep pages
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 100000;

-- ✅ Keyset pagination (constant time)
SELECT * FROM orders
WHERE created_at < '2023-06-15'
ORDER BY created_at DESC LIMIT 20;
```

## Advanced: Index Condition Pushdown (ICP)

```sql
-- MySQL 5.6+: Push WHERE condition into storage engine
-- Before ICP: Index returns rows → Server evaluates WHERE
-- With ICP: Storage engine evaluates WHERE during index scan

EXPLAIN SELECT * FROM orders
WHERE user_id = 1 AND total > 1000;
-- Extra: Using index condition  ← ICP active
```

## Optimizer Hints (When You Know Better)

```sql
-- MySQL
SELECT /*+ MAX_EXECUTION_TIME(1000) */ * FROM huge_table;
SELECT /*+ JOIN_ORDER(u, o) */ * FROM users u JOIN orders o ON u.id = o.user_id;
SELECT /*+ INDEX(o idx_orders_user_status) */ * FROM orders o WHERE o.user_id = 1;

-- PostgreSQL: Set enable_* params
SET enable_seqscan = off;  -- Force index usage (testing only)
SET enable_hashjoin = off;

-- SQL Server
SELECT * FROM orders WITH (INDEX(idx_orders_user_id)) WHERE user_id = 1;
```

## Statistics & Cardinality

```sql
-- MySQL: Update statistics
ANALYZE TABLE orders;

-- PostgreSQL: Auto-analyze runs, but can force
ANALYZE orders;

-- Check statistics
-- MySQL
SHOW STATS_META;  -- 8.0+
-- PostgreSQL
SELECT * FROM pg_stats WHERE tablename = 'orders';
```

> **Outdated stats = bad plans**. Run ANALYZE after bulk loads.
